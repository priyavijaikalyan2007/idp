- 2026-07-09 — **SPI handoff defense-in-depth from the red-team review (RT-008/009/010/011).** Four hardening changes to the MCP handoff, all TDD (152 unit + 3 IT green): **(RT-008)** the callback now binds the picker-result to the *specific* request — the authenticator stores the request `jti` in an auth-session note at suspend, and the callback requires `picker_request_jti` **and** `oauth_state` to match server-side state, so a compromised/buggy consent app can't get a signed result for a *different* request accepted (HMAC validity alone was insufficient binding); it also validates `chosen_tenant_id` format before it reaches a token claim. **(RT-009)** `granted_scopes` are now subset-validated against the client's actually-assigned client scopes (default+optional) and rejected on unknowns/duplicates — a consent-service bug can no longer mint arbitrary/elevated scopes into an access token. **(RT-011)** `knobby.web.host` is strictly validated (bare hostname only — no scheme/port/path/userinfo/whitespace) and pinned per-realm via an in-code allowlist for internet-facing realms (`knobby-prod`→`prod.knobby.io`, `knobby-dev`→`dev.knobby.io`), **failing closed** — so a misconfigured/compromised admin can't redirect signed handoff tokens to an attacker host. **(RT-010)** initial stopgap: the in-memory replay cache logged a startup warning that `maxScale=1` was a security invariant. - 2026-07-03 — Corrected the flow-binding guidance for the MCP short-circuit (docs only; no code change). Real-world testing reversed the recommendation from **Option A** (realm-wide browser-flow binding) to **Option B** (per-client binding): a malformed MCP flow bound realm-wide returned HTTP 400 for *every* login, and realm-default assignment of `mcp-default` breaks the SPI's own MCP-client detection (the web client would also carry the scope). - 2026-07-01 — The MCP tenant-picker Authenticator now short-circuits for non-MCP clients (spec §5.1). `McpTenantPickerAuthenticator.authenticate()` opens with a guard: if the client lacks the `mcp-default` client scope (as a default or optional scope), it calls `context.success()` and returns, so regular `knobby-{env}-web` logins and other non-MCP clients pass through untouched. This lets `browser-mcp-tenant-pick` be bound realm-wide (setup guide D.8 Option A) without hijacking normal logins — **`mcp-default` is now the on/off switch for the whole handoff**, so MCP clients must have that scope assigned for the picker to fire. ### Added

- 2026-07-08 — **B1 / AllowedGrantTypes — atomic grant-type enforcement at DCR registration (ADR-017).** `McpClientRegistrationPolicy.beforeRegister` (and `beforeUpdate`) now **reject with a 400** any DCR'd client that enables a non-authorization-code grant: Direct Access Grants (password/**ROPC**), implicit, client_credentials (service accounts), the device authorization grant, and CIBA. This closes the one real bypass of the picker + `/mcp/consent` enforcement: those are gated by the *browser* auth flow, so a non-browser grant (ROPC issues tokens with no browser flow at all) would skip them entirely — which matters now that Keycloak's built-in consent is dropped (ADR-016). It's a **security invariant, deliberately not admin-tunable**, and runs on update too so a client can't widen its grants later. Folded into the existing MCP CRP (one provider for all DCR-time registration policy) rather than a separate SPI. TDD: 7 new unit tests + 1 real-DCR testcontainers IT (a `password`-grant registration is rejected); **142 unit + 3 IT green**. `smoke-mcp.sh` also asserts `directAccessGrantsEnabled=false` on the live client.
- 2026-07-07 — **Monotonic image revision tagging + rollback tooling.** Every pushed image now also gets a `kc<keycloak-version>-<NNNNN>` tag (e.g. `kc26.6.4-00007`) alongside the existing `timestamp-commit` and `latest` tags. The `NNNNN` counter is **globally monotonic** (a strict total order over all builds, derived from the registry so it needs no local state) and the `kc<ver>` prefix records which Keycloak base each build used — so when a base-image bump breaks prod you can redeploy the highest-numbered tag on the last-good base. `push.sh` computes + applies + pushes it and records it in `build.json`. New `revisions.sh` lists revisions newest-first (joined with their timestamp-commit tag + digest); new `rollback.sh <tag>` redeploys an already-pushed tag to Cloud Run **without rebuilding**.
- 2026-07-06 — **`McpClientRegistrationPolicy`** — a custom Keycloak Client Registration Policy that closes the MCP DCR **bootstrapping circular dependency** (ERRATA-001, SPI design §5.8). It marks every anonymously-registered MCP client **atomically at registration**: inside the registration transaction it sets the `knobby.mcp="true"` attribute, assigns the default (`mcp-default` + author bundle) and optional (`knobby:admin`) client scopes, and binds the `browser-mcp-tenant-pick` browser flow — so the client's *first* authorization already routes through the tenant picker. Atomic means either fully-marked or rolled back (a missing scope/flow throws) — no partial states. Scope lists + flow alias are admin-tunable `ComponentModel` config with the settled defaults as fallback. Deployed as an **anonymous** Client Registration Policy (governs only self-registered DCR clients). This is the bootstrap half of the provisioning split; the `/mcp/consent` wizard owns the rest. TDD: 15 unit tests + 1 real-DCR testcontainers integration test; 129 unit + 2 IT green. ADR-011. Update: B1 grant-type enforcement was folded into this same CRP on 2026-07-08 (ADR-017).
- 2026-06-10 — `check_image.sh`: forensic image-inspection helper (OCI traceability labels, baked-in `/opt/keycloak/providers/` contents, Quarkus build artifacts). Born during the production incident below; pipe two invocations into files and diff to answer "what differs between these images?" in seconds.

### Fixed

- 2026-07-08 — **Corrected the built-in-consent suppression to a config fix, and added the grant-type bypass guard (ERRATA-006 correction / ADR-016).** `smoke-mcp.sh` now asserts the DCR'd client's `consentRequired`, which confirmed the ERRATA-006 claim was wrong: the CRP's `setConsentRequired(false)` does **not** win — the `mcp-hardening` `consent-required` executor's `autoConfigure` re-applies `consentRequired=true` after the CRP, so Keycloak's "Grant Access" screen still double-ups the knobby `/mcp/consent` wizard. The authoritative fix is a **config change**: remove the `consent-required` executor from the profile *and* the `consent-required` Client Registration Policy if present. Dropping Keycloak's consent doesn't weaken enforcement — the picker + wizard are gated by the auth flow (the picker is `REQUIRED`, suspends, and no token issues until the app returns a valid HMAC-signed picker-result), which is stronger and non-redundant. The control that actually prevents a bypass is **grant-type restriction**: `smoke-mcp.sh` now also asserts `directAccessGrantsEnabled=false` (ROPC would skip the browser flow entirely — no picker, no wizard). Corrected the now-wrong docs: ERRATA-006, setup guide D.5/D.6, `keycloak.prd.md`; the CRP retains `setConsentRequired(false)` as belt-and-suspenders with an honest comment. Deferred B1 (AllowedGrantTypes CRP) should enforce the grant-type restriction atomically.
- 2026-07-08 — **Diagnosed the fresh-session `/mcp/consent` dead-end (ERRATA-007) — app-side fix pending.** With the Keycloak side fully working (post-broker picker fires, redirects to `/mcp/consent?token=…` with a valid, user-carrying handoff JWT — verified in `chrome.har` + IdP/app logs), the flow still fails for a user not already logged into the knobby.io web app: the wizard gates itself behind a **knobby.io app session** instead of trusting the signed token. That triggers a second interactive login (the MCP flow is suspended at the picker, so no Keycloak SSO session exists to authenticate against silently), and that login **loses the `return_url`** and lands on the app home page — so `mcp-picker-callback` is never hit (0 times in the HAR) and the flow hangs. The fix is entirely app-side (KnobbyApi): `/mcp/consent` must authenticate from the HMAC-signed `?token=` (already `aud`-scoped + carrying `sub`), not an app session. ERRATA-007 documents both flows (already-logged-in and not-logged-in) that the fix must make correct. No Keycloak/SPI change.
- 2026-07-07 — **`smoke-mcp.sh` loopback listener no longer fails to bind on WSL2.** The interactive test hardcoded callback port `53789`, which on WSL2 falls in a Windows/Hyper-V *excluded* TCP range (`netsh int ipv4 show excludedportrange tcp`) that no WSL process can bind — so `bind()` failed with `Address already in use` even though nothing was listening (and the earlier `fuser`/`lsof` reclaim couldn't help — there was no process to kill). The port now defaults to a **dynamic OS-assigned free port** (`bind(("127.0.0.1", 0))`), which is always outside every excluded/in-use range; the script does DCR each run so it registers whatever port is chosen. Also hardened the listener (explicit `SO_REUSEADDR` + a short bind-retry) and made a persistent bind failure report an actionable message instead of a generic "no code captured". Override still available via `CALLBACK_PORT`.
- 2026-07-07 — **Settled the fresh-session / brokered-login tenant-picker gap (ERRATA-005) — spike done, config-only fix.** Fresh (cookieless) MCP logins never reached `/mcp/consent`: after a brokered IdP login, Keycloak doesn't run browser-flow executions placed after the IdP-redirect step (issue #10250), so the picker in `browser-mcp-tenant-pick` was skipped. A 26.6.0 SDK spike (decompiling `LoginActionsService`, `AuthenticationProcessor`, `AuthenticationFlowURLHelper`, `IdentityBrokerService`) confirmed the fix is to also host the **same** `Knobby MCP Tenant Picker` in a per-IdP **Post Broker Login Flow**, and that the authenticator works there **unmodified**: the brokered login keeps one auth session (client/user/re-entrancy-note all resolve), and `getLastExecutionUrl` rebuilds the resume URL from the `current.flow.path` note (`post-broker-login`) so suspend/resume works. **No code change to the authenticator logic, no `McpPickerCallbackResourceProvider` change, and no app-side change** — only doc-in-code touch-ups (the §5.1 MCP-detection guard is now **load-bearing** in the post-broker flow, per-IdP and shared with web logins) plus admin-console config (setup guide D.2a: one shared `post-broker-mcp-tenant-pick` flow bound on Google + Microsoft, each execution needs its own `knobby.web.host`). Acceptance test must run in a **cookieless** session. ERRATA-005, ADR-015.
- 2026-07-07 — **Fixed MCP default-scope placement + attempted built-in-consent suppression (ERRATA-006).** Two CRP client-shape defects surfaced once the flow ran end-to-end. (1) A DCR'd client's default-client-scopes were missing `mcp-default` + the author bundle even though they were effective (correct `aud`): Keycloak's OIDC DCR pre-binds the request's `scope` values as **optional** client scopes before the CRP runs, and `ClientModel.addClientScope` is a **no-op when a binding already exists**, so it never promoted them to **default** (`knobby:admin`, which the client doesn't request, was placed correctly — the tell). `McpClientRegistrationPolicy` now does **remove-then-add** so its default/optional placement is authoritative. (2) The CRP also set `consentRequired=false`; later production smoke testing on 2026-07-08 proved that this does **not** override the `consent-required` executor/CRP when configured. Current fix: remove consent-required from MCP DCR config per ADR-016 and setup guide D.5/D.6. The IT now sends `scope` (reproducing prod — it previously sent none, which is why it passed while prod failed) and asserts default-scope placement + `consentRequired=false` in the no-consent-forcer test environment. TDD: 2 new unit tests; 135 unit + 2 IT green. ERRATA-006, ADR-014 superseded in part by ADR-016.
- 2026-07-07 — **Fixed the `/mcp/consent` ⇄ Keycloak infinite redirect loop (ERRATA-004).** Once the ERRATA-003 correlation echo let `mcp-picker-callback` resume the flow, a loop surfaced: the callback resumes via `getLastExecutionUrl`, which makes Keycloak re-invoke the tenant-picker authenticator's **`authenticate()`** (a challenged execution resumes through `authenticate()`, not `action()`) — and it unconditionally issued a *fresh* picker-request and re-challenged, so the browser bounced back to `/mcp/consent` forever. `McpTenantPickerAuthenticator.authenticate()` now opens with a **resume guard**: if the callback recorded the consent (new auth note `knobby.mcp.picker.completed`, written by `McpPickerCallbackResourceProvider`), it calls `context.success()` and finishes the step. Explicit marker (not "is the tenant note set?") because the validator's Jackson path bypasses the builder's `requireString`, so a signed-but-malformed result could carry a null tenant and still loop. Writer + reader share one public constant (`AUTH_NOTE_PICKER_COMPLETED`) so they cannot drift. **No app-side change** — the app's redirect, claims, and echo are all correct; the loop was in fact evidence the ERRATA-003 fix works. TDD: 3 new unit tests; 133 unit tests green. ERRATA-004.
- 2026-07-06 — Diagnosed the production `client=null` HTTP 400 on the `mcp-picker-callback` final hop (ERRATA-003). Root cause is a **contract desync**, not a resume bug: the SPI callback recovers the suspended session + client from `kc_client_id`/`kc_tab_id`/`auth_session_id` claims the app must **echo** from the picker-request into the signed picker-result, but web spec §2.2/§3.3 never told the app to send them — so `getClientByClientId(null)` returned null. Fixes applied here: web spec §2.2 step 5 + §3.3 now require the three echoed claims (sourced from the **server-held** picker-request, never the client POST body — a session-fixation guard); the SPI now returns a precise `missing_correlation` error (distinct from `client_not_found`) with a spec-pointing WARN instead of the cryptic failure; and the stale SPI design §5.3 (which documented jti-based correlation + `AuthenticationProcessor.continueAuthentication` — neither shipped) was reconciled to the real `AuthenticationSessionManager` + `getLastExecutionUrl` design. **The end-to-end fix also needs the KnobbyApi app (separate repo) to echo the three claims** — that's the change that actually clears the 400. 1 new SPI unit test; all suites green. ADR-012.
